deploys · tag a release, the pi picks it up

How it works - Release a version - Is it live? - By hand on the Pi - When it doesn't deploy - Which apps - Install

The rule: a push to main deploys nothing, a version tag deploys. Push as often as you like. When a state of main should go live, tag it v1.4 and the Pi deploys it within 5 minutes, even when you're away.

How it works

  • Every 5 minutes the joanpi-deploy job asks GitHub which v* tags each app has. That is one small request per app, a few KB; nothing is downloaded when nothing changed.
  • If an app has a tag newer than the last one it saw, it fetches, checks the checkout out at that tag and runs docker compose up -d --build.
  • Then it checks the release: every container has to be running (and healthy, if it has a health check), still running 15 seconds later, and the app's port has to answer.
  • If the check fails, it goes back to the version that was running before and rebuilds it. The failed tag is not tried again. A newer tag, or a deploy by hand, takes over.

At a tag, the checkout isn't on a branch ("detached"). That's on purpose: the folder holds exactly the tagged code. So in these folders, don't git pull or git checkout by hand any more. Use deploy (below), which keeps track of what is running.

Release a version

From the laptop

git tag v1.4
git push origin v1.4

From the phone

  • GitHub → the repo → Releases → Draft a new release.
  • Choose a tag: type v1.4, pick Create new tag on publish, target main.
  • Publish release. The notes are optional.

Claude in the app can push to main but can't create tags or releases, so tagging stays your step: Claude pushing to main deploys nothing. Claude Code on the laptop can tag when you ask.

Tag names

  • v + numbers and dots: v1.4, v1.4.1, v2. Anything else (v1.5-rc1, latest) is ignored, so it can be used to mark things without deploying them.
  • "Newer" means a higher number, not a later date: v1.10 comes after v1.9. A tag lower than the one running is ignored.
  • Never move or reuse a tag. To fix a release, make a new one (v1.4.1).

Is it live?

  • Pi Chart → Jobs, line Deploy new release tags of the apps: the last run's summary (6 up to date · kiosk v1.4 ok) and its log.
  • When something needs you, that job shows as failed, and the homepage shows its red line until it's sorted out.
  • On the Pi: deploy status.

By hand on the Pi

What runs where

deploy status

Deploy the newest tag now (no 5-minute wait; also retries a failed or held tag)

deploy kiosk

A precise version, main, or back to an older tag

deploy kiosk v1.4
deploy kiosk main
deploy kiosk v1.3

deploy kiosk main is for trying out untagged code on the Pi; it shows as main@abc1234. It stays until the next new tag. The same checks and rollback apply as for the automatic run.

Log of the automatic runs

journalctl -u joanpi-deploy -n 50

When it doesn't deploy

Rolled back

Read the reason in deploy status, then the app's own log:

cd ~/inkbook-digest && docker compose logs --tail 50

Fix it on main and tag a new version. The rollback restores the code, not the data: if the release had already changed a database when it failed, the old version may not like it. That's why Vélothèque's migrations are held.

Held

The release migrates a database. Deploy it when you can watch, ideally right after a backup:

deploy velo

Blocked: a new setting

cd ~/inkbook-digest
git diff HEAD v1.4 -- .env.example
nano .env
deploy kiosk

Blocked: edited by hand

cd ~/inkbook-digest && git status
git stash

Then deploy kiosk. git stash list keeps the edits in case they mattered; anything worth keeping belongs in the repo.

Check failed several times in a row

The Pi couldn't ask GitHub for 30 minutes: no internet, or the repo's key or URL broke. Try it yourself:

cd ~/telex && git ls-remote --tags origin

Which apps

The list is /etc/joanpi/deploy.toml: Telex, Vélothèque, BabyDash, Kiosk, Double Feature, Regularity Conditions and Lux Archive. The name to type is the left column of deploy status (telex, velo, babydash, kiosk, cine, econ, lux); the folder name works too.

Still updated another way:

  • JoanPi home and Tally follow main on their own every 15 minutes (joanpi-home-pull, joanpi-gym-pull): they're pages, nothing to build.
  • Pi Chart's code and anything under ops/ in this repo: see Recipes → Deploy.
  • Vélothèque's ops/ (its backup job): sudo ops/install-backup.sh after a release that changes it.
  • AdGuard and Baby Buddy: third-party images, updated by hand.

Add an app

sudo nano /etc/joanpi/deploy.toml

A [repos.name] block with dir (folder in the home folder) and port. Its first check records the version that's running and deploys nothing; tags after that deploy.

Install (once)

Each app's checkout should be clean (git status shows no edited files). Then:

cd ~/joanpi-home && git pull && sudo ops/install.sh

It creates /etc/joanpi/deploy.toml, the deploy command and the 5-minute timer, and lists each app with ok or NOT FOUND. For a NOT FOUND, fix its dir in /etc/joanpi/deploy.toml. It needs Docker Compose 2.17 or newer, and says so if the Pi's is older.

The first run deploys nothing: it records what each app runs and its newest tag. Only tags made after that deploy. Double Feature already has tags up to v9.0.0, so its next release is v9.1 or higher.
